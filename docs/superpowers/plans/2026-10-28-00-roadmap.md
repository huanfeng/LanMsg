### C2. 标识类型 `lanmsg_proto::ids`（P1 定义）

```rust
pub struct UserId(pub [u8; 32]);    // = 用户 Ed25519 公钥字节
pub struct DeviceId(pub [u8; 32]);  // = 设备 Ed25519 公钥字节
pub struct ConvId(pub [u8; 32]);
pub struct BlobHash(pub [u8; 32]);  // BLAKE3
pub struct MsgId { pub author: DeviceId, pub seq: u64 }
```
- 四个 32 字节类型都实现：`Copy, Clone, Eq, Ord, Hash, Serialize, Deserialize, Debug`，`fn to_hex(&self) -> String`（64 位小写 hex），`fn from_hex(s: &str) -> Result<Self, IdError>`，`Display` = hex。
- `UserId`、`DeviceId` 另有 `fn short(&self) -> String`：`base32_nopad_lower(blake3(self.0)[..16])`，26 字符，用于界面显示指纹。
- `MsgId` 的字符串形式：`"{author_hex}:{seq}"`，`Display` / `FromStr` 互逆。
- `ConvId` 构造函数：
  - `ConvId::dm(a: &UserId, b: &UserId) -> ConvId` = `blake3("lanmsg-dm" || min(a,b) || max(a,b))`
  - `ConvId::self_devices(u: &UserId) -> ConvId` = `blake3("lanmsg-self" || u)`
  - `ConvId::localsend(fingerprint: &str) -> ConvId` = `blake3("lanmsg-ls" || fingerprint.as_bytes())`（P5 使用）
  - `ConvId::random() -> ConvId`（访客、中转站用）

- P2 Task 1 追加的协议类型（`ConvMeta`、`ConvKindWire`、`ContactRecord`、`ContactStateWire`、`Revocation`、`ContactRequest`、`ContactResponse`、`BlobQuery`、`BlobHave`、`PairMsg`、`PairMethodWire`、`PairBundle`、`body_is_hidden`，`SyncOffer.meta: Option<ConvMeta>`，`SystemEvent` 的 `ContactUpdated`/`ProfileUpdated`/`LocalDeleted`）以 P2 计划 Task 1 为准；P5 Task 1 追加的 `Station*`/`AddressBook` 类型以 P5 计划为准。
- 序号规则：`MsgId.seq` 是作者设备上**全局单调递增**的序号（从 1 开始，跨会话唯一），因此 `MsgId` 全局唯一；`Envelope.conv_seq` 是 `(conv, author)` 内**连续**的序号（从 1 开始）。`VersionVector` 记录的是每个作者在该会话中**连续收齐**的最大 `conv_seq`（乱序先到的消息照常入库，但不推进向量），同步时对方补发 `conv_seq > vv[author]` 的全部消息。
- 签名规则：`sig` 覆盖的是"把 `sig` 字段置为全零后整个结构的 CBOR 编码"。统一由 `lanmsg_proto::sign` 模块的 `sign_with_zeroed_sig` / `verify_with_zeroed_sig` 实现（P1 Task 3），不得在别处另写。
- `DeviceCert.sig` 由**用户密钥**签；`Envelope.sig`、`Announce.sig` 由**设备密钥**签。

### C4. 帧 `lanmsg_proto::frame`（P1 定义骨架，后续阶段追加变体）

线格式：`u32 BE 长度 | u16 BE 帧类型号 | CBOR 负载`，长度 = 2 + 负载长度，上限 `MAX_FRAME_LEN`。

```rust
pub enum Frame {
    Hello(Hello),                 // 1
    Ping(u64),                    // 2
    Pong(u64),                    // 3
    SyncOffer(SyncOffer),         // 10  P1 定义结构，P2 实现逻辑
    SyncPush(SyncPush),           // 11
    Ack(Ack),                     // 12
    Presence(Status),             // 13
    BlobQuery(BlobQuery),         // 20  P2
    BlobHave(BlobHave),           // 21  P2
    Pair(PairMsg),                // 30  P2
    ContactRequest(ContactRequest),   // 40  P2
    ContactResponse(ContactResponse), // 41  P2
    Revocation(Revocation),       // 42  P2
    CertUpdate(Vec<DeviceCert>),  // 43  P2
    AddressBook(AddressBook),     // 50  P5
    Station(StationMsg),          // 60  P5
    Error { code: u16, message: String }, // 99
    Unknown(u16),                 // 解码遇到未知类型号时产生，收到后忽略
}
```
- 通道字节（P2）：TLS 握手完成后，拨号方先写 1 字节 `CHANNEL_CONTROL` 或 `CHANNEL_DATA`；控制通道随后按本节帧格式通信，数据通道使用 P2 Task 1 定义的 `DataFrame`（独立类型号空间 1–6、99；`RangeStart` 帧之后紧跟原始字节）。P1 不写通道字节；P2 Task 3 引入通道字节后，控制连接与数据连接共用同一监听端口。
- 类型号是线协议的一部分，**永不复用**。新阶段追加变体时在上表登记类型号。
- `Hello { proto: u16, caps: Vec<String>, cert: Option<DeviceCert>, user_display_name: String, listen_port: u16 }`。`listen_port` 是发送方主服务的实际监听端口：被拨入的一方只能看到对端的临时源端口，后续需要回拨（数据连接、地址记忆）时一律使用 `PeerInfo.dial_addr = (对端 IP, hello.listen_port)`。`cert = None` 表示该设备尚未初始化（还没有用户身份），此时对端只接受 `Pair`、`Ping/Pong`、`Error` 帧，其余帧一律回 `Error` 并忽略（P2 配对使用）。
- 能力字符串：`"sync/1"`、`"blob/1"`、`"pair/1"`、`"station/1"`。
- 数据连接（Blob 传输）使用独立的帧集合，见 P2 计划。

### C5. 客户端 API `lanmsg_api`（P1 建 crate；各阶段按下表实现）

IPC 与 FFI 共用。ID 字段在 API 层一律为 `String`（C2 的 hex / `MsgId` 字符串形式），以便 FFI。所有类型 `#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]`，并在 `uniffi` feature 下 `#[cfg_attr(feature = "uniffi", derive(uniffi::Record))]`（枚举用 `uniffi::Enum`）。

```rust
pub struct ApiRequest { pub id: u64, pub body: Request }
pub struct ApiResponse { pub id: u64, pub result: Result<Response, ApiError> }
pub enum IpcFrame { Request(ApiRequest), Response(ApiResponse), Event(Event) }
pub struct ApiError { pub code: ErrorCode, pub message: String }
pub enum ErrorCode { NotInitialized, AlreadyInitialized, NotFound, InvalidArgument,
    PeerOffline, Rejected, Io, Internal }
```

**Response 的形状**：除 `Ok` 外，每个 Response 变体都是**具名单字段** `{ value: T }`，例如 `Response::SelfInfo { value: SelfInfo }`、`Response::MsgId { value: String }`、`Response::Peers { value: Vec<PeerView> }`（UniFFI 不能可靠支持元组变体）。下表 `X(T)` 的写法即表示 `X { value: T }`。

### C7. IPC（P1 定义）

- 端点名：Unix `$XDG_RUNTIME_DIR/lanmsg/lanmsgd.sock`（无该变量时 `<data_dir>/lanmsgd.sock`）；macOS `<data_dir>/lanmsgd.sock`；Windows 命名管道 `\\.\pipe\lanmsgd-<用户名>-<blake3(data_dir 规范化路径) 前 8 位 hex>`（带 data_dir 摘要，使测试和多实例可隔离）。由 `lanmsg_api::ipc::endpoint_name(data_dir: &Path) -> String` 统一计算。
- 帧：与 C4 相同的 `u32 BE 长度 | CBOR(IpcFrame)`（无类型号字段），由 `lanmsg_api::ipc::IpcCodec` 实现。
- 客户端：`lanmsg_api::ipc::IpcClient::connect(endpoint) -> Result<IpcClient>`，`async fn call(&self, req: Request) -> Result<Response, ApiError>`，`fn events(&self) -> broadcast::Receiver<Event>`。`lanmsg-cli`、`lanmsg-desktop` 都用它。

### C8. 数据目录（P1 定义）

`lanmsg_core::paths::default_data_dir() -> PathBuf`：Windows `%APPDATA%\LanMsg`、macOS `~/Library/Application Support/LanMsg`、Linux `$XDG_DATA_HOME/lanmsg`（用 `directories` crate）。目录内：`lanmsg.db`、`keys/`（FileKeyStore）、`cache/thumbs/`、`station/`、`logs/`。Android 由 Kotlin 侧传入。

## 全局 Review Focus（每个阶段的审阅者都要检查）

1. **对端发送畸形或超大数据**：任何来自网络的帧/HTTP 请求都必须有长度上限与解析失败处理，失败只断开该连接，绝不 panic、绝不拖垮 Service。
2. **重复与乱序**：同一条消息经多条路径到达（直接 + 经自己另一台设备转交）必须幂等，只存一条、只发一次事件。
3. **磁盘写到一半中断**（断电、杀进程、磁盘满）：数据库事务与 `.part` 文件保证重启后状态一致，不出现"显示已下载但文件损坏"。
4. **网络切换**（Wi-Fi 换网、休眠唤醒、网卡增减）：发现与连接自动恢复，不需要重启应用。
5. **未初始化 / 被吊销 / 陌生设备**调用受保护功能：返回明确错误（`NotInitialized` / `Rejected`），不泄露数据。

各阶段计划在自己的 Review Focus 中补充本阶段特有的项，并为每项在所属任务里写测试。
