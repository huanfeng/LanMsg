## 1. 意图

LanMsg 是一款**以局域网为主、无服务器**的聊天式传输工具。

核心场景【已定】：一个人在家里 / 公司同时有电脑和手机，频繁在它们之间传文件、图片、视频、文字。现有工具的问题：

- LocalSend：一次性投递，没有记录，对方要守着点"接收"；
- 微信文件传输助手：走外网、压缩图片视频。

LanMsg 把每次传输变成**会话里的一条消息**：有时间线、有历史、可搜索，文件就在消息里，并有一个整理过的**文件视图**。同事等其他局域网用户同样可以作为联系人互发。

后续通过 **Hub**（公网服务器或 NAS）扩展到跨网络、群聊、远程中转站；通过 IPv6/DDNS/STUN 支持个人设备的公网组网。

## 2. 目标 / 非目标 / 反目标

### v1 目标【已定】

1. 同一局域网内打开即可看到自己的其他设备和其他用户，零配置。
2. 发文件像发微信一样顺手；接收方无需守着屏幕，按策略自动接收。
3. 联系人是"人"，一个人的多台设备共享会话，历史在自己的设备间自动同步。
4. "我的设备"配对与信任；陌生人首次来消息需确认。
5. 文件视图：按类型 / 来源 / 会话整理所有收发过的文件。
6. 文件中转站：按需拉取，源设备需在线。
7. Web 临时会话：无客户端的设备用浏览器与某台 LanMsg 设备互传。
8. 兼容 LocalSend v2 协议，与 LocalSend 用户互传。
9. 跨网段 / VPN：手动添加 + 一定的自动检测。
10. 平台：Windows / macOS / Linux 桌面 + Android。
11. 局域网内跑满带宽（指标见 §17）。
12. 无界面时尽量少占内存（后台进程与界面进程分离）。

### v1 非目标（架构预留，见 §19）

Hub、群聊、机器人、iOS、鸿蒙、IPv6+DDNS / STUN 公网直连、远程中转站、消息撤回之外的高级 IM 功能（表情回应、引用回复等可后续加）。

### 反目标（做到了功能但仍算失败）

- 后台常驻吃掉几十上百 MB 内存。
- 局域网传输明显低于网卡带宽。
- 为了支持图片视频把 windui 库搞得臃肿（【已定】：媒体解码放在应用侧外部 crate）。
- 首次使用需要注册账号、填服务器地址等配置步骤。
- 在公司网络里明文传输。

## 3. 核心概念

| 概念 | 定义 |
|---|---|
| **用户（User）** | 一个人。由**用户密钥**（Ed25519）标识，`user_id = base32(blake3(user_pubkey))[..26]`。有显示名、头像。 |
| **设备（Device）** | 用户名下的一台终端。由**设备密钥**（Ed25519）标识，持有一张由用户密钥签发的**设备证书**。 |
| **联系人（Contact）** | 另一个用户（含其全部设备）。类型：`user` / `localsend`（LocalSend 设备，见 §14）/ `guest`（Web 临时会话，见 §13）/ 预留 `bot`、`hub_group`。 |
| **会话（Conversation）** | 一份只追加的消息日志。v1 两种：与某联系人的单聊；**"我的设备"会话**（自己所有设备之间，相当于微信文件传输助手，是核心场景的主入口）。另有中转站视图（§11）。 |
| **消息（Message）** | 由作者设备签名的记录，`msg_id = (author_device_id, seq)`。 |
| **Blob** | 文件内容，按 BLAKE3 哈希寻址。消息只携带 Blob 元数据，内容按需从**持有者**拉取。 |
| **持有者（Holder）** | 本地有某 Blob 完整内容的设备。 |
| **路径等级（PathClass）** | 一条连接经过的网络类型：`lan` / `vpn` / `internet` / `relay`（§6.5）。 |

**设计主线**：一切都是"元数据同步 + 内容按需拉取"。聊天文件、中转站、文件视图、多设备同步共用这一套机制。

## 4. 总体架构

### 4.1 进程模型【已定方向，细节为设计决定】

```
桌面端：
┌──────────────────────────────┐   本地 IPC    ┌───────────────────────────┐
│ lanmsgd（后台进程，常驻）      │◄────────────►│ lanmsg（界面进程，按需启动）│
│ - lanmsg-core 全部功能         │ Win: 命名管道 │ - windui 窗口              │
│ - 托盘（原生 API，不加载 windui）│ Unix: UDS    │ - lanmsg-media 解码显示    │
│ - 系统通知                     │              │ - 关闭窗口即退出进程        │
│ - 缩略图生成与缓存              │              │                           │
└──────────────────────────────┘              └───────────────────────────┘

Android：一个 App 进程
  前台服务（= 后台进程，持有 core）  ◄── 直接 FFI 调用 ──►  Activity / Compose UI
```

- 托盘用系统原生 API：Windows `Shell_NotifyIcon`、macOS `NSStatusItem`、Linux StatusNotifierItem（D-Bus，回退 XEmbed 可不做）。理由：托盘若依赖 windui 会把窗口栈与渲染缓冲带进常驻进程。
- 点托盘 / 点通知 → `lanmsgd` 拉起 `lanmsg` 界面进程（已运行则激活窗口）。
- `lanmsgd` 可**无头运行**（Linux / NAS：无托盘，作为 systemd 服务），可作为常开的中转站主机。

### 4.2 Crate 划分【设计决定】

单一 Cargo workspace：

| Crate | 职责 |
|---|---|
| `lanmsg-proto` | 线协议类型、帧编解码、版本与能力协商。无 IO。 |
| `lanmsg-core` | 身份与信任、发现、连接、同步、Blob 传输、存储、策略、Web 服务、事件总线。对外暴露 `Service` API。 |
| `lanmsg-api` | 客户端 API 类型（命令 / 查询 / 事件）及其 IPC 编解码。桌面 IPC 与移动 FFI 共用同一组类型，**API 只定义一次**。 |
| `lanmsg-media` | 图片解码（JPEG/PNG/WebP/GIF/HEIC）、视频首帧提取、缩略图生成，输出 RGBA。供 `lanmsg`（显示原图）使用；另编出一个短命辅助进程 `lanmsg-thumb`，由 `lanmsgd` 按需拉起生成缩略图后退出，解码器内存不驻留在后台进程。 |
| `lanmsg-localsend` | LocalSend v2 适配器（发现 + HTTPS 收发），作为 core 的一个可插拔"外部协议端"。 |
| `lanmsg-web-assets` | Web 临时会话的静态页面（单 HTML + JS + CSS，构建期内嵌）。 |
| `lanmsgd` | 桌面后台进程二进制：托盘、通知、IPC 服务、自启动。 |
| `lanmsg-desktop` | 桌面界面进程二进制（windui）。产物名 `lanmsg`。 |
| `lanmsg-ffi` | UniFFI 绑定（Kotlin，后续 Swift）。鸿蒙后续走 ohos-rs N-API。 |
| `lanmsg-cli` | 开发 / 测试用命令行客户端（连 `lanmsgd` 的 IPC），也服务于无头部署。 |

另：`android/`（Kotlin + Jetpack Compose 工程），`docs/ui-architecture.md`（移动端 UI 架构文档，见 §15.2）。

- 媒体解码【设计决定】：JPEG/PNG/WebP/GIF 用纯 Rust 解码（`image` crate 及其后端）；HEIC 与视频首帧优先用系统 API（Windows WIC / Media Foundation、Android `MediaMetadataRetriever` / `ImageDecoder`、后续 macOS ImageIO / AVFoundation）；Linux 及系统 API 不支持时调用 ffmpeg（优先系统已安装的；GPL 许可下也允许随包附带）。都失败则显示通用文件图标，不阻塞发送。
- 异步运行时：tokio。【设计决定】
- 存储：SQLite（rusqlite bundled，WAL，FTS5）。【设计决定】
- TLS：rustls（ring 或 aws-lc-rs 后端，【留给实现】按跨平台编译难度选）。

### 4.3 `Service` API 形状【设计决定】

core 对上层只暴露三类东西：

- **命令**：`send_text`、`send_files`、`download_blob`、`pair_start`、`accept_request`、`station_put` ……
- **查询**：会话列表、消息分页、文件视图查询、联系人、设备 ……（直接读 SQLite 的只读视图，桌面 IPC 下由 daemon 执行）
- **事件流**：新消息、传输进度、在线状态变化、请求弹窗、配对状态 ……

界面进程不直接打开数据库，避免两个进程写同一个库。

## 5. 身份与信任

### 5.1 密钥【设计决定】

- 首次启动：生成设备密钥。若用户选择"这是我的第一台设备"，同时生成用户密钥，并为本设备签发设备证书；若选择"加入我已有的设备"，进入配对流程（§5.2）。
- 设备证书：`{device_pubkey, user_pubkey, device_name, device_type, created_at}` 由用户密钥签名。
- **用户私钥在本人所有设备上都有一份**（配对时传过去）。取舍：简单、任一设备都能配新设备；代价是任一设备失窃即可签发新设备、吊销其他设备 → 由吊销 + 后续"轮换用户密钥"缓解（v1 实现吊销，轮换列为后续）。为了将来能改为"仅主设备持有"或做轮换而不迁移协议：设备证书与吊销记录都带 `key_epoch` 字段（v1 恒为 0），线协议与数据库从 P1 起即带版本号与迁移机制。
- 私钥存放：Windows DPAPI / 凭据管理器、macOS Keychain、Linux Secret Service（不可用时回退到 0600 文件）、Android Keystore 包裹。

### 5.2 "我的设备"配对【设计决定】

两种方式，底层同一条流程：

1. 设备 A（已有用户）点"添加我的设备"，生成一次性 128 位口令 `S`（5 分钟有效），显示二维码：`lanmsg://pair?d=<A设备指纹>&a=<地址:端口列表>&s=<S>`。
2. 设备 B 扫码（或在 B 上点"加入"，从发现列表里选 A）。
3. B 连接 A，建立 TLS（此时双方证书尚未互信，仅取得对方公钥与握手 transcript 哈希 `H`）。
4. 校验：
   - **扫码方式**：双方用 `S` 计算 `HMAC(S, H || 本方公钥)` 互相发送并校验。二维码只在 A 的屏幕上，能扫到即证明物理在场。
   - **数字比对方式**（无摄像头 / 两台电脑）：双方屏幕显示由 `H` 派生的 6 位数字（SAS），用户在两边确认一致后各点"是"。
5. 校验通过 → A 把用户私钥、用户资料、已知设备证书列表、联系人列表加密发给 B；A 为 B 签发设备证书；A 广播"新设备"记录给其他自己的设备。
6. B 加入后自动开始历史同步（§8）。

信任传递：我的设备都持有用户公钥，任何持有有效设备证书且未被吊销的设备都是"我的设备"。

### 5.3 吊销

任一自己的设备可"移除设备" → 生成用户签名的吊销记录，同步给自己的设备与联系人。被吊销设备的连接一律拒绝。

### 5.4 联系人与陌生人【已定 + 设计决定】

- 陌生人首次发来消息 / 文件：弹窗「接收一次 / 加为联系人 / 拒绝 / 屏蔽」。【已定】
- "加为联系人"是**双向确认**（类似好友申请）【设计决定】：A 发起 → B 收到请求 → B 同意后双方互为联系人，交换用户公钥与设备证书；之后对方新增设备（持有效证书）自动被认。B 同意前，A 在 B 处仍按陌生人规则处理（A 的消息以请求形式出现，B 选"接收一次"不建立关系）。B 拒绝 / 屏蔽后 A 侧显示"未通过"，不再自动重发。
- 每个联系人可配：自动接收开关、超过 N MB 仍询问。自己的设备间默认全自动接收。【已定】
- 默认策略：陌生人请求只在 `lan` 路径上接受；`vpn` 路径的陌生人需手动添加后才可通信；`internet` / `relay` 路径不接受陌生人。【设计决定】

### 5.5 在线状态

- **在线**（默认）：组播通告，所有人可见。【已定】
- **隐身**：不通告、不响应陌生人探测；仅自己的设备之间可见并同步。联系人看到离线，其消息留在对方待发队列，切回在线后送达。【设计决定】
- 预留 **忙碌**（通告但不弹通知）。

## 6. 发现与连接

### 6.1 局域网发现【设计决定】

- UDP 组播：IPv4 `239.255.53.20:53320`，IPv6 `ff02::5320`（link-local）同端口。
- 通告内容（CBOR，签名）：协议版本、`user_id`、显示名、头像哈希、设备指纹、设备类型、服务端口列表、状态。
- 周期：启动 / 网络变化时立即通告 + 每 30 秒一次；收到陌生通告时单播回应一次（加速发现）。离线判定：90 秒无通告且无活动连接。
- 每块网卡分别通告（多网卡、虚拟网卡分别处理，§6.4）。

### 6.2 服务端口

- 主服务 TCP `53320`（被占用则随机端口，通告中带实际端口）。
- Web 临时会话 TCP `53321`（仅开启时监听）。
- LocalSend 兼容：TCP/UDP `53317`（仅在空闲时占用，见 §14）。

### 6.3 跨网段 / VPN【已定需求，设计决定】

组播通常不跨 VPN / 路由，因此：

1. **手动添加**：输入 `IP/主机名[:端口]`，连接后显示对方身份，再走陌生人 / 联系人流程。
2. **地址记忆**：保存每个联系人设备最近成功连接过的地址（含路径等级），离线时按退避策略单播重试（1s → 5min 封顶）。
3. **地址交换**：自己的设备之间同步"联系人设备 → 已知地址"表；联系人之间在连接时交换自己的其他设备地址（仅对联系人）。
4. **单播通告目标**：用户可配置一组地址 / 网段，向它们单播发送通告。
5. **网段扫描**（可选，手动触发）：用户指定 CIDR（最大 /22），向每个地址的 53320 发起探测。
6. **隧道网卡识别**：枚举网卡，识别 Tailscale（`100.64.0.0/10`、`tailscale*`）、ZeroTier（`zt*`）、WireGuard（`wg*`）、通用 `tun*/utun*`；发现时在设置中提示"可在此网络中扫描"。

### 6.4 连接建立

- 每对设备之间维持**一条控制连接**（TCP + TLS 1.3，双向认证）；大文件传输另开**数据连接**（§9）。
- TLS 证书：由设备密钥自签，自定义校验器只比对公钥 → 设备指纹，并校验设备证书链（用户签名、未吊销）。
- 同一对设备有多条可达地址时，按路径等级优先：`lan` > `vpn` > `internet` > `relay`。
- 连接层抽象为"候选地址列表"（类似 ICE candidate）：v1 只有直连 TCP 候选，后续加入 IPv6 公网 / DDNS / STUN 打洞 / Hub 中继候选，不改上层。

### 6.5 路径等级标记【已定】

| 等级 | 判定 |
|---|---|
| `lan` | 经组播发现，或对端地址与本机某网卡同网段的私有地址 |
| `vpn` | 私有 / CGNAT 地址但不同网段，或经隧道网卡，或手动添加的私有地址 |
| `internet` | 公网 IPv4 / 全局 IPv6 / DDNS / STUN（后续） |
| `relay` | 经 Hub 转发（后续） |

- UI：联系人 / 设备在线指示与传输进度上显示角标（`lan` 不显示，其余显示小标签）。
- 策略按等级生效：自动下载阈值、是否接受陌生人、是否允许做 Web 宿主（仅 `lan`）。

## 7. 线协议

【设计决定】

- 控制连接：长度前缀帧（u32 BE）+ CBOR 负载（`ciborium` 或 `minicbor`，【留给实现】）。
- 首帧 `Hello`：协议版本、能力列表（`sync/1`、`blob/1`、`station/1` …）、设备证书。双方取能力交集。
- 主要帧类型：`Hello`、`Ping/Pong`、`SyncOffer`（版本向量）、`SyncPush`（消息批）、`Ack`、`BlobQuery`（谁有）、`Presence`、`PairXxx`、`ContactRequest/Response`、`Revocation`。
- **消息信封**：`{conv_id, author_device, seq, hlc, kind, body, sig}`，`sig` 为作者设备签名，因此消息可经第三方设备（如自己的另一台设备）转交而仍可验证。预留 `enc` 字段供 Hub 场景的端到端加密（§19）。
- 前向兼容：未知帧类型 / 未知字段忽略；`kind` 未知的消息显示为"不支持的消息类型，请升级"。

## 8. 消息与同步

### 8.1 会话 ID【设计决定】

- 单聊：`blake3("dm" || sort(user_pubkey_a, user_pubkey_b))`。
- 我的设备：`blake3("self" || user_pubkey)`。
- Web 访客：宿主本地随机 ID。LocalSend：`blake3("ls" || 对方指纹)`。

### 8.2 消息类型（v1）

`text`、`file`（单个或多个 Blob，含图片 / 视频的媒体信息与内嵌缩略图）、`folder`（目录清单：相对路径 + Blob 元数据列表）、`recall`（撤回，引用目标 msg_id）、`read`（已读水位）、`system`（加入设备、联系人建立等）。

### 8.3 排序

每条消息带 HLC（混合逻辑时钟）时间戳；显示按 `(hlc, author_device, seq)` 排序，避免设备时钟偏差导致乱序。

### 8.4 投递与多设备同步【设计决定】

- 发给人 = 投递给对方**所有在线设备**；任一设备 Ack 即"已送达"。全部离线 → 存发送方待发队列，任一设备出现即投递。
- 每台设备为每个会话维护**版本向量** `{author_device → 已有最大 seq}`。两台共享某会话的设备连上后交换向量、补发缺失消息。
  - 我的设备之间：同步**所有**会话（含与联系人的单聊）。
  - 与联系人设备之间：只同步双方的单聊。
- 结果：同事发到我电脑的消息，我手机回到网络后从电脑补齐；我在手机上发出的消息，电脑也能看到。
- 已读：任一自己的设备读过即同步已读水位给自己的设备和对方。
- 删除：v1 仅本地删除（可选"同时从我的其他设备删除"，以同步的本地删除记录实现）。撤回：2 分钟内，发 `recall`，各端隐藏原消息。

### 8.5 首次同步新设备

新配对设备从现有设备拉取全部会话的消息元数据（不拉 Blob 内容，按 §9.4 策略决定）。消息量大时分批、按会话最近活跃优先。

## 9. 文件（Blob）传输

### 9.1 元数据

`{blob_hash(BLAKE3), size, name, mime, media{w,h,duration}, thumb(≤32KB JPEG, 内嵌), holders[]}`

- 缩略图由**发送方**生成（图片 256px 长边、视频首帧），接收方不必能解码原始格式也能显示。
- 发送方默认**不复制**原文件，记录本地路径 + `(size, mtime)`；被请求时校验，若已变化则重算哈希，不一致则对外宣告"不再持有"。

### 9.2 哈希

- 发送大文件时后台流式计算 BLAKE3（同时生成分块校验数据，`bao-tree` 或等价方案，【留给实现】），消息先以"准备中"状态出现在本地，哈希完成后才发出。
- 分块校验以支持：边收边验、断点续传、多源并行。

### 9.3 传输【设计决定】

- 数据连接：独立的 TCP + TLS 1.3 连接（同样双向认证），请求 `{blob_hash, range}`，响应原始字节流。
- 并行：单文件按 8MB 分段，默认 4 条数据连接并行；多个小文件在一条连接上流水线传输。
- 多源：若多台持有者在线，可从多个源并行拉不同分段（优先 `lan` 路径）。
- 断点续传：已校验分段持久化记录，中断后继续。
- 写盘：先写 `.part` 临时文件，完成校验后原子重命名。
- 调优点（【留给实现】，以 §17 指标为准）：socket 缓冲、读写块大小、TLS 记录大小、是否用 kTLS / `sendfile`。

### 9.4 自动下载策略【已定 + 默认值为设计决定】

| 内容 | 默认 |
|---|---|
| 文字、缩略图 | 总是同步 |
| 图片原图 | < 10MB 自动下载 |
| 视频、文件 | < 50MB 且 Wi-Fi / 有线时自动下载 |
| 超出阈值 | 点击才下载 |

- 阈值可按路径等级（`lan` 用上表，`vpn` 默认减半）、按联系人覆盖。
- 自己的设备上发出的文件：其他自己的设备同样适用此策略（不全量复制）。

### 9.5 保存位置

- 下载完成的文件：`<下载目录>/LanMsg/` 下，按会话名分子目录（可配置）。Android 存入 MediaStore（图片 / 视频进相册可配）。
- 缩略图与小图缓存：应用数据目录 `cache/`，有上限（默认 1GB，LRU）。

## 10. 文件视图【已定需求】

- 汇总所有会话（含中转站）的文件元数据，是一个查询视图，不另存数据。
- 筛选：类型（图片 / 视频 / 文档 / 压缩包 / 其他）、联系人 / 会话、来源设备、状态（已下载 / 未下载 / 源离线）、时间。
- 显示：图片视频为网格，文件为列表；每项标注来源（"来自 张三 · 存于 我的台式机"）。
- 操作：打开、打开所在文件夹、下载、转发到会话、放入中转站、删除本地副本。
- 搜索：文件名 FTS。

## 11. 文件中转站【已定需求，设计决定】

**本质**：某台设备（主机）上的一个"货架"。放进去的只是元数据，内容留在主机上，其他设备需要时才拉取。和聊天的区别："我推给你" vs "你需要时来拿"；中转站条目可管理（置顶、删除、过期），而不是时间线。

- 任一桌面设备（含无头 `lanmsgd`，如 NAS）可开启一个或多个中转站。v1 不在 Android 上做主机。
- 中转站作为特殊联系人（机器人样式）出现在会话列表；**自己的所有设备自动可见**。
- 条目：文件、文件夹、文字片段。属性：添加者、时间、可选过期时间。
- 添加方式：拖到中转站窗口、右键"发送到 LanMsg 中转站"（Windows Shell 扩展列为后续，v1 用"发送到"菜单 / 拖拽）、从会话或文件视图转入；手机也可以往中转站上传（文件存入主机的中转站目录）。
- 存储模式（每条可选）：**引用原文件**（默认，零复制，原文件移走则失效）/ **复制到中转站目录**。
- 拉取：手机看到清单（含缩略图），点击下载；主机离线时清单可看，条目标"源离线"。
- 共享给联系人：v1 不做，数据模型预留 ACL（`owner_only` / `contacts[]`）；远程中转站经 Hub 实现（§19）。

## 12. 存储

- SQLite 单库：`users`、`devices`、`certs`、`revocations`、`contacts`、`conversations`、`messages`、`version_vectors`、`blobs`、`blob_holders`、`blob_local`（本地路径 / 状态）、`transfers`、`station_items`、`known_addresses`、`settings`，FTS5 虚表索引文本与文件名。
- 迁移：内置版本化迁移脚本。
- 静态加密：v1 不做数据库加密（依赖系统账户隔离），私钥走系统密钥库。【设计决定】
- 数据目录：Windows `%APPDATA%\LanMsg`，macOS `~/Library/Application Support/LanMsg`，Linux `$XDG_DATA_HOME/lanmsg`，Android 应用私有目录。

## 13. Web 临时会话【已定需求，设计决定】

场景：手机到了新环境，旁边电脑没装客户端；或任意设备之间临时互传。

- 任一设备（手机或电脑）开启"网页传输" → 显示二维码与地址 `http://<lan-ip>:53321/#k=<一次性口令>`。
- 浏览器打开 → 宿主弹窗"浏览器请求连接 · 允许 / 拒绝"。允许后建立临时会话。
- 功能：互发文字、文件、图片；拖拽 / 多选上传；大文件分块上传 + 断点续传；下载支持 Range；图片预览。
- 宿主侧：记为"访客 · 日期时间"会话，历史保留在宿主。网页端不存任何东西。
- 时效：页面关闭或 30 分钟无活动即作废口令；宿主可随时结束。
- 传输加密【设计决定】：页面走 HTTP（自签 HTTPS 的浏览器警告对临时用户不友好），但**内容在应用层加密**，以满足"公司网络不明文传输"的反目标：
  - 二维码 / 链接里的口令放在 URL 片段 `#k=`，浏览器不会把片段发给服务器；页面用它派生 256 位密钥，所有消息与文件分块用 XSalsa20-Poly1305（tweetnacl secretbox，纯 JS，因为非安全上下文里 WebCrypto 不可用）加解密。
  - 手动输入地址时，宿主显示 8 位字母数字配对码：双方做 X25519 临时密钥交换，以 scrypt(配对码) 作为 HKDF 盐派生会话密钥，再双向 HMAC 确认；连续 5 次确认失败即作废并重新生成配对码，单 IP 限速。（实现规划时核实过：没有可靠维护的浏览器端 SPAKE2 实现，故采用此方案。）
  - 再叠加宿主手动允许 + 短时效。可选的自签 HTTPS 列为 v1 之后（§19）。
  - 页面体积预算放宽到 < 300KB。
- 实现：宿主 core 内嵌 HTTP 服务（如 axum），WebSocket 推送消息事件；页面为单个内嵌静态包，不依赖外网，目标 < 200KB。
- 仅允许在 `lan` 路径上开启。Android 作宿主时要求前台服务运行。

## 14. LocalSend 兼容【已定需求，设计决定：v1 实现】

依据 LocalSend 协议 v2（实现前须对照 `github.com/localsend/protocol` 官方文档逐字段核实，并评估 v2.1 PIN 支持）：

- 发现：UDP 组播 `224.0.0.167:53317` JSON 通告（alias、version、deviceModel、deviceType、fingerprint、port、protocol、download、announce）；HTTP `POST /api/localsend/v2/register` 回应。
- 接收：HTTPS 自签证书，实现 `prepare-upload`（返回 sessionId 与每文件 token）、`upload`、`cancel`。
- 发送：作为客户端调用对方同名接口。文字以带 `preview` 的 text 类型发送 / 接收。
- 在 LanMsg 中：LocalSend 设备作为 `localsend` 类型联系人出现（带标记），收发进入其会话时间线；不支持已读、撤回、中转站、同步。接收行为按陌生人 / 联系人规则（LocalSend 为 TOFU，指纹即身份）。
- 端口冲突：若 53317 已被占用（本机运行着 LocalSend），则不启动兼容监听，设置中提示；仍可作为客户端向 LocalSend 设备发送。
- 设置中可关闭兼容（默认开）。
- 只在 `lan` 路径生效。

## 15. 客户端

### 15.1 桌面界面（windui）

- 布局：左侧图标栏（会话 / 联系人 / 文件 / 中转站 / 设置）+ 列表栏 + 主区。
- 会话主区：消息流（文字气泡、图片网格、视频卡片含时长、文件卡片含状态：未下载 / 下载中进度 / 已下载 / 源离线、系统消息）、输入区（多行文本、emoji、粘贴图片、拖入文件、选择文件 / 文件夹）。
- 消息流用 windui 虚拟列表；图片按需由 `lanmsg-media` 解码为 RGBA → `Image::from_rgba`。
- 首次启动向导：设置显示名 → "这是我的第一台设备 / 加入已有设备"。
- 托盘菜单：打开、状态（在线 / 隐身）、开启网页传输、退出。

### 15.2 移动端（Android v1）

- Kotlin + Jetpack Compose，通过 UniFFI 调 `lanmsg-ffi`。minSdk 26（Android 8.0），targetSdk 跟随当前最新。【设计决定】
- 分发：v1 只发 APK，但为以后上 Google Play 留余地【已定】。前台服务类型声明为 `specialUse`（附 `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` 说明"局域网设备间实时消息接收"），服务实现与类型声明解耦，便于上架时按审核结果改为 `connectedDevice` 或退回"省电"档；不使用有每日 6 小时上限的 `dataSync` 做常驻。
- 前台服务持有 core；三档后台模式【已定需求，设计决定】：**实时**（默认，前台服务常驻 + 低优先级常驻通知）/ **省电**（仅亮屏、充电或在指定 Wi-Fi 时保持连接，其余时间 WorkManager 约 15 分钟同步一次）/ **关闭**（仅打开 App 时同步）。按会话免打扰。
- 系统分享入口：从其他 App "分享到 LanMsg"。
- 需要的权限：网络、组播锁（`WifiManager.MulticastLock`）、通知、前台服务、相机（扫码）、媒体读取。
- **`docs/ui-architecture.md`**【已定：移动端原生实现，按 UI 架构文档由 AI 同步实现】：定义与平台无关的页面清单、导航结构、每页的状态模型（对应 `lanmsg-api` 的查询 / 事件）、组件规范、交互细节与文案。Android / iOS / 鸿蒙各自据此实现。v1 写此文档并实现 Android。

### 15.3 windui 的边界【已定】

- 不为 LanMsg 往 windui 加聊天专用逻辑或媒体解码。
- 仅当缺口是**通用**能力时补到 windui（候选：外部文件拖入窗口、文件拖出、系统剪贴板图片读写、富文本选区复制、气泡类自适应宽度约束），每项单独评估并在 windui 仓库内按其规范开发。
- 其余（图片 / 视频解码、缩略图、聊天组件组合）在 `lanmsg-desktop` / `lanmsg-media` 实现。

## 19. 扩展预留（v1 不实现）

- **Hub**：公网服务或 NAS。用户以用户密钥登录；Hub 作为 `relay` 候选转发信封，并存储离线消息；经 Hub 的信封启用端到端加密（信封 `enc` 字段：对接收方用户的各设备分别加密会话密钥，算法后定）。局域网下只有 TLS 一层，经 Hub 时 TLS + 端到端两层，这就是"局域网放低加密、Hub 必须加密"的落地方式。
- **群聊**：Hub 维护成员列表与消息扇出；会话 ID 由 Hub 分配；消息仍由作者设备签名。
- **远程中转站 / 远程发文件**：Blob 拉取经 Hub 中继或 Hub 缓存。
- **机器人**：`bot` 联系人类型 + 本地 HTTP 推送接口（默认只监听内网，带令牌），用于接收 AI / 外部系统推送。
- **公网组网**：候选地址扩展 IPv6 全局地址、DDNS 主机名、STUN 打洞；路径标记为 `internet`，策略默认更保守。
- **iOS / 鸿蒙**：复用 `lanmsg-ffi`（Swift via UniFFI；鸿蒙 via ohos-rs）与 `docs/ui-architecture.md`。
- **用户密钥轮换**、数据库静态加密、Windows Shell 右键扩展、Web 临时会话的可选自签 HTTPS。
